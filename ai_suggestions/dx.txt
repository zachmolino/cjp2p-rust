## The core problem

Right now there are two different audiences you could target, and they need different things:

1. **App builders** - web/game devs who want to use the WebSocket API to make HTML apps on top of your running node. They never touch the protocol itself.
2. **Protocol implementors** - people who want to write a compatible node in Python, Go, JS, etc.

You're probably closer to #1 being viable, and #1 eventually leads to #2.

---

**3. The LAN/offline demo is your strongest hook - use it as the pitch**

"Two phones on a hotspot, no internet, game works in under 30 seconds" is a conference-talk-worthy demo that no other tool can match cleanly. That specific story (offline game night, field ops, conference without wifi) will attract a different crowd than "decentralized p2p." Write that demo as a short video or GIF. The quickstart doc is great but it's text.

**4. The AI-writes-your-app angle is already working - lean into it harder**

The quickstart prompt is genuinely compelling. Make a gallery: "here are 5 apps Claude wrote for cjp2p in one prompt." Blog post or HN post with that framing gets you developer attention quickly. "LLM-friendly API" is a real differentiator right now.

**6. Don't underestimate Termux/Android as a differentiator**

Most p2p projects treat Android as an afterthought. You have a working APK. That's a community (Termux users, Android hackers) that would actually care. A post in r/termux or the Termux GitHub discussions would find people who specifically want LAN-local tools that work on phones.

---

## What I'd skip for now

- A Python/Node SDK wrapping the WebSocket API - this is low-leverage until there are users asking for it.
- Economics/scarcity/reputation features - those are in the TODO list but they add complexity before you have adoption.
- Trying to compete with libp2p or IPFS on features - your angle is simplicity and the offline/LAN case, not feature parity.
